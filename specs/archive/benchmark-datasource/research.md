## Questions

### RQ1: How do comparable tools pin benchmark datasets and baselines?

- **source**: https://github.com/colbymchenry/codegraph · **claim**: codegraph's benchmark runs a WITH/WITHOUT-MCP A/B (Claude Opus headless, 4 runs/arm, median) over exactly 7 repos — VS Code, Excalidraw (TypeScript), Django (Python), Tokio (Rust), OkHttp (Java), Gin (Go), Alamofire (Swift) — cloned `--depth 1` with **no commit pins and no machine/hardware stamp**, only a date ("Re-measured 2026-08-05"); metrics are wall time, tool calls, file reads, tokens, cost; a sanitized PATH + PreToolUse hook was needed to block CLI contamination (without-arm reached the CLI in 26/28 runs). · **relevance**: SC-4, FR-006/T3, FR-004 — the "7-repo benchmark class" pins by clone date, so cairn commit-pinning + machine stamping strictly dominates it; also evidence that pinning must be enforced, not assumed. · **confidence**: high
- **source**: https://pytest-benchmark.readthedocs.io/en/latest/comparing.html (+ /usage.html) · **claim**: pytest-benchmark saves runs under `.benchmarks/<machine-id>/` (e.g. `Linux-CPython-3.4-64bit` — platform + Python impl/version + arch) with autosave file name `0001_<commit-id>_<YYYYMMDD_HHMMSS>.json` or `0001_<name>.json` for `--benchmark-save=name`; `--benchmark-compare=NUM` diffs a saved run and `--benchmark-compare-fail=min:5%`/`mean:0.001` turns regressions into failures; machine info is a first-class recorded field (extension hook `pytest_benchmark_update_machine_info()`), never a normalization input. · **relevance**: FR-004 — closest prior art for committed-JSON baselines with (machine-id, commit, timestamp) addressing and threshold compare. · **confidence**: high
- **source**: https://github.com/beir-cellar/beir (README) · **claim**: BEIR pins each retrieval dataset by fixed name + **md5 checksum of the hosted zip** (`https://public.ukp.informatik.tu-darmstadt.de/thakur/BEIR/datasets/<name>.zip`, e.g. scifact `5f7d1de60b170fc8027bb7898e2efca1`) rather than semver; loading goes through one `GenericDataLoader` interface so format is version-locked by checksum. · **relevance**: FR-001/FR-004 — checksum-pinning (not semver) is the accepted way to pin a dataset version; cairn's manifest hash check is the same move. · **confidence**: high
- **source**: https://psf.github.io/pyperf → https://raw.githubusercontent.com/psf/pyperf/master/README.rst · **claim**: pyperf embeds collected system metadata in every result JSON ("Automatically collect metadata on the computer and the benchmark", inspectable via `pyperf metadata` / `pyperf collect_metadata`) and treats unstable systems as a hard error path ("Detect if a benchmark result seems unstable"); `compare_to` runs significance tests on differences. · **relevance**: FR-004/RQ5 — metadata-embedded-in-artifact + significance-testing precedent. · **confidence**: high
- **source**: https://codspeed.io/docs/ + https://codspeed.io/docs/instruments/cpu · **claim**: Codspeed avoids cross-machine normalization entirely by changing the metric: the CPU instrument runs each benchmark **once** and simulates CPU behavior (per-instruction cost weights from Agner Fog/uops.info tables + cache/memory miss penalties) to produce "a clear and consistent metric for the execution speed of your code, independent of your hardware"; a walltime mode exists for I/O-heavy work on isolated "Macro Runners". · **relevance**: FR-004 posture — the credible alternative to stamp-and-warn is hardware-independent simulation, out of scope for cairn (advisory timing) but confirms warn-don't-normalize is the mainstream choice. · **confidence**: high

### RQ3: Standard deterministic, path-order-independent tree hashes for CI content-pinning?

- **source**: https://git-scm.com/book/en/v2/Git-Internals-Git-Objects · **claim**: Git's tree object is exactly a digest-of-digests over **sorted** entries — `SHA("tree <size>\0" + concat("<mode> <name>\0<20-byte sha>"))` — so the hash depends on the *set* of (mode, name, content-hash) entries, never on staging/creation order. · **relevance**: FR-001 — canonical model for cairn's "path-order-independent content hash": sort, hash leaves, hash the sorted manifest. · **confidence**: high
- **source**: https://git-scm.com/docs/git-archive · **claim**: `git archive <commit-or-tag>` is byte-deterministic (commit-recorded timestamps, paths sourced from the tree not the directory listing, `export-ignore` from committed attributes, internal gzip with `--format=tar.gz` avoiding external-gzip mtimes); archiving a bare tree uses *current* time and is NOT reproducible. · **relevance**: FR-001 — simplest tool-based option: `git archive --format=tar <pin> | sha256sum`; caveat: same git version required and it needs the content to live in a git commit. · **confidence**: high
- **source**: https://nix.dev/manual/nix/2.35/protocols/store-path (from https://nix.dev/manual/nix/latest/store/store-path) · **claim**: Nix store-path digests are SHA-256 over the NAR serialization (sorted entries, contents, exec bits) *composed with* the store directory and name into a fingerprint, deliberately opaque — powerful but heavy machinery, and the digest depends on store-path context. · **relevance**: FR-001 — the "gold standard" precedent; overkill for a manifest equality check, but validates sorted-serialization as the canonical approach. · **confidence**: high
- Bazel REAPI Merkle-tree digest page (https://bazel.build/remote/create) returned 404 on fetch; ctar: no credible source found — decide from first principles. Note: none of the above is needed for correctness — a pure-Python loop emitting `sha256("<mode> <relpath>\0<sha256(content)>")` over sorted paths is Git-tree-shaped, stdlib-only, and runs identically on GitHub Actions ubuntu and macOS (no git/nix dependency). · **relevance**: FR-001 implementation choice for tech-spec. · **confidence**: high (recommendation-shaped observation, not a citation)

### RQ4: Ground-truth formats for retrieval evals (BEIR / MS MARCO / minimal schema for cairn)?

- **source**: https://raw.githubusercontent.com/beir-cellar/beir/main/beir/datasets/data_loader.py · **claim**: BEIR's canonical triple is `corpus.jsonl` (`_id`, `title`, `text`), `queries.jsonl` (`_id`, `text`), and qrels **TSV with a header** then `query_id \t corpus_id \t score` where score is parsed as `int(row[2])` — graded integers, with binary relevance as the {0,1} special case; queries without qrels are dropped. · **relevance**: FR-003 — the de-facto schema cairn's ground truth should stay shaped like (queries file + expectations keyed by query id → target ids + integer grade). · **confidence**: high
- **source**: https://trec.nist.gov/data/deep2019.html (linked from https://microsoft.github.io/msmarco/) · **claim**: TREC Deep Learning (MS MARCO) qrels use a **4-point graded scale** 0–3, and the classic pitfall is that passage grade 1 ("Related") "is actually NOT Relevant" — binary metrics must cut at ≥2 (`trec_eval -l 2`); files named `2019qrels-pass.txt` / `2019qrels-docs.txt`. · **relevance**: FR-003 — argues for graded (not binary) expectations in cairn's ground truth so "related but not the answer" symbols don't poison recall@10/MRR. · **confidence**: high
- **source**: https://microsoft.github.io/msmarco/ · **claim**: the MS MARCO landing page documents label provenance (passages marked as answering the question; NIST judgments for graded) but no on-page qrels column spec — format details live in the TREC/github-linked pages above. · **relevance**: RQ4 completeness; no separate claim needed beyond above. · **confidence**: med
- Minimal-schema synthesis (first principles, BEIR-shaped — no single source): `queries.jsonl` = `{query_id, level: L1|L5, kind: definition|callers|impact|flow|knowledge, text, rationale}` + `expectations.tsv` = `query_id \t symbol_id \t grade` where `symbol_id` is cairn's stable `file#symbol` identity at the pinned commit and grade ∈ {1 = must-return, 2 = primary target}; recall@10 over grade≥1, MRR ranks grade-2 first. Rationale belongs in queries.jsonl (per-FR-003), not in the qrel. · **relevance**: FR-003 schema for eval.py + validator. · **confidence**: design guidance, grounded in the two sources above

### RQ5: Machine-profile fields and cross-machine warning practice?

- **source**: https://pytest-benchmark.readthedocs.io/en/latest/comparing.html, /usage.html, /faq.html · **claim**: pytest-benchmark partitions storage **by machine id** (platform + Python + arch, e.g. `Linux-CPython-3.4-64bit`) — comparisons are same-machine by construction; the FAQ addresses noise (VMs "make machine performance inconsistent" → use bare metal; Turbo Boost thermal effects) and offers custom timers, never cross-hardware normalization. · **relevance**: FR-004 — model for cairn: machine profile as *partition key / warning trigger*, not an adjustment factor. · **confidence**: high
- **source**: https://pyperf.readthedocs.io/en/latest/system.html (+ README) · **claim**: `pyperf system check/tune` reads/sets exactly: CPU scaling **governor** (performance vs powersave), min frequency (`scaling_min_freq`), **Turbo Boost** (MSR + intel_pstate `no_turbo`), IRQ affinity / irqbalance, `isolcpus`+`rcu_nocbs` CPU isolation, ASLR state, perf event rate, and AC-power presence — the doctrine is *stabilize the machine, then raw numbers are comparable*; plus `--affinity` pinning and auto-collected metadata per run. · **relevance**: FR-004/RQ5 — the accepted field list for a machine-profile stamp (arch, cpu model, core count, governor, turbo, power class) and the warn-don't-normalize precedent. · **confidence**: high
- **source**: https://codspeed.io/docs/instruments/cpu (from /docs/what-is-codspeed) · **claim**: Codspeed makes cross-machine numbers comparable by abandoning wall-clock on shared runners (single deterministic simulated run, "independent of your hardware"); its walltime mode buys comparability with dedicated isolated "Macro Runners" instead. · **relevance**: RQ5 — normalization is only credible via dedicated/deterministic runners; on rotating CI runners the only sound options are same-profile warning (pytest-bench/pyperf style) or runner-class pinning — matching the spec's `reference-local` runner-class assumption. · **confidence**: high
- raptorjit benchkit (https://github.com/raptorjit/benchkit): 404 on fetch — no credible source found; decide from first principles (the pyperf check/tune field list above covers the same ground). asv's `asv.conf.json` page (https://asv.readthedocs.io/en/stable/asv.conf.json.html) documents no machine section; only a sidebar `asv.machine` API module — low-confidence, not relied upon. · **confidence**: low / noted for transparency

## Options summary

### Baseline artifact format & addressing (FR-004)
- pytest-benchmark-style JSON — storage dir per machine-id + `<seq>_<commit>_<ts>.json`; ecosystem-familiar, but brings pytest schema baggage.
- pyperf-style single JSON with embedded metadata — self-describing artifact, simplest to stamp dataset-version into; no directory partitioning for free.

### T2 vendored snapshot repo (FR-002)
- markupsafe (1.0 MB, BSD-3) — smallest, clean dual Python/C impl of one API; thinnest call depth of the top three.
- yarl (2.75 MB, Apache-2.0) — best call depth + docstrings per byte, very active; closest to the 3 MB line.
- uvloop (1.8 MB, Apache-2.0) — deepest callback/inheritance graph; Cython adds parsing surface.
- httptools (0.16 MB, MIT) — tiny insurance arm; likely fails the call-depth bar.

### Tree-hash mechanism (FR-001)
- stdlib sorted-manifest digest (Git-tree-shaped) — no tool deps, byte-identical on ubuntu/macOS; reimplements known-good design.
- `git archive --format=tar <pin> | sha256` — one-liner, but requires content committed and same git version.
- Nix/NAR-style — most rigorous, far too much machinery for an equality assert.

### Ground-truth schema (FR-003)
- BEIR-triple adapted (queries.jsonl + graded TSV expectations keyed by symbol ids) — standard shape, tool-friendly; rationale needs an extra field outside the qrel.
- Custom per-query JSONL (expectations + rationale inline, one file) — validator-friendly, single source of truth; diverges from IR-tool conventions.

### Machine-profile stamp & mismatch policy (FR-004)
- Minimal stamp {arch, cpu model, core count, os, runner_class} + loud warn on mismatch — pytest-benchmark's partition-and-warn model; cheap, honest.
- Rich pyperf-style stamp (+governor, turbo, power state) recorded-but-advisory — more diagnostic signal, mostly unactionable on hosted CI.
- Normalize across machines — no mainstream tool does this on shared runners (Codspeed escapes via simulation, not normalization); treat as out of scope.
