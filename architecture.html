cairn — System Architecture

A local, structural, agent-first codebase intelligence system: source → typed call graph in SQLite → layered knowledge (compass, wiki, memory) → 26-tool MCP server for AI agents.

The defining property: every output is verifiable. Edges carry resolution labels (exact/ambiguous/unresolved); LLM-synthesized docs are fact-checked by a deterministic critic against the graph. An agent may hallucinate, but a hallucinated symbol can never land in a compass doc.

2. The five layers

L1 · 9 tools

Graph

The structural core: definitions, callers/callees, blast radius, semantic search, the explore aggregator, cross-repo deps, graph viz. Backed by .kg SQLite.

L2 · 5 tools

Compass + KB + Router

Module navigation (get_compass), KB search, the cross-layer router (ask_compass), flow tracing/generation. Backed by .knowledge/ + graph.

L4 · 7 tools

Memory

Tribal memory across tiers: record / recall / digest / promote / demote / decay. Live refs-verified fraction on every recall.

L5 · 5 tools

Knowledge

Business docs + procedural workflows: add / search / delete / status / trace_workflow. Bridges to cross-repo deps.

Two front doors. explore (pure L1) answers structural questions in one round trip; ask_compass classifies intent and routes across all layers.

3. How the layers interact

Layers are decoupled by storage, not by network. L1 owns source of truth; L2/L4/L5 are markdown on top that reach into L1 for verification and bridging. Exactly three cross-layer interactions exist:

flowchart LR L1["L1 Graph
(.kg)"] L2["L2 Compass/KB
(.knowledge/)"] L4["L4 Memory
(.knowledge/)"] L5["L5 Knowledge
(.knowledge/)"] L2 -- "1. critic fact-checks
compass/wiki refs
against symbols+files" --> L1 L4 -- "2. refs-verified fraction
recomputed live each recall" --> L1 L5 -- "3. knowledge_search bridges
business docs to
cross_repo_deps" --> L1
The three cross-layer dependencies — all one-directional, all into L1.
  1. L2 → L1 (critic gate). Every generated compass/wiki is fact-checked: backtick references verified against the graph. A hallucinated symbol can't land in a doc.
  2. L4 → L1 (live verification). recall_memory / memory_digest recompute how many of a memory's references still exist right now — a low value flags stale memory.
  3. L5 → L1 (graph bridge). knowledge_search appends cross_repo_deps to business docs declaring affects_repos.

Build sequence

sequenceDiagram participant CLI as cairn build participant B as builder participant DB as :memory: DB participant R as resolver participant Disk as on-disk .kg CLI->>B: build_graph(progress) B->>DB: get_build_db() — FK off, sync OFF, 256MB cache B->>B: scan_workspace (emit "scan") loop every file — parallel if >10 B->>B: parser.parse() — emit "parse_progress" B->>B: detect_routes + detect_service_calls end B->>B: emit "parse_done" loop every parsed file B->>DB: insert_parsed_file — emit "insert_progress" Note over DB: triggers sync symbols_fts end loop every repo B->>R: resolve_repo_edges — emit "resolve_start" R->>DB: build indexes — symbol/import/members/ancestor R->>DB: resolve_edge × N — 6 tiers R->>DB: UPDATE edges SET target_id, resolution R-->>B: emit "resolve_done" end B->>Disk: backup_to() — emit "persist"
atomic .tmp + os.replace B->>Disk: build_dataflow_index + build_transitive_closure B->>Disk: PRAGMA wal_checkpoint(TRUNCATE)
Build sequence: the full-workspace path runs in :memory: and swaps to disk atomically.
Resolver tiers (in order): type-aware (receiver dispatch) → same-file → import-aware → same-repo → global. The resolver stops at the first tier with a unique match; multiple matches → ambiguous (no fallthrough). cairn update (incremental) does not rebuild the derived indexes — only cairn build does.

ask_compass(query) — the cross-layer router

sequenceDiagram participant Agent as 🤖 AI Agent participant AC as ask_compass() participant CL as classify_intent participant L1 as L1 Graph participant L2 as L2 Compass/KB participant L4 as L4 Memory participant L5 as L5 Knowledge Agent->>AC: ask_compass("context for AuthModule") AC->>CL: regex over INTENT_PATTERNS — first match CL-->>AC: layer ∈ {L1,L2,L4,L5,ALL} alt single layer matched AC->>AC: query that one layer else ALL — complex / no match AC->>L1: _query_graph_hybrid AC->>L2: _get_compass / _search_wiki AC->>L4: _search_memory AC->>L5: _search_knowledge end opt all layers empty — degraded AC->>AC: re-run graph + memory + knowledge end AC-->>Agent: consolidated cross-layer result
ask_compass() classifies intent and dispatches to one or all layers; degrades gracefully if results are sparse.

6. The LLM boundary & critic loop

cairn never calls an LLM itself. Where synthesis helps (compass/wiki), it uses a decoupled task queue, and a deterministic critic fact-checks every result against the graph before commit.

flowchart TB GEN["Need synthesis?
e.g. generate compass"] GEN --> Q{"LLM available
in-process?"} Q -- "yes — droid/opencode/claude" --> LOOP["sync revise loop
max 4 cycles"] Q -- "no" --> TASK["async task queue
cairn task create"] TASK --> CLAIM["agent runs
cairn task claim"] CLAIM --> COMP["agent runs
cairn task complete --result-file"] COMP --> CRITIC LOOP --> CRITIC["🔍 deterministic critic
verifies refs vs graph"] CRITIC --> D{"passed?"} D -- "yes" --> WRITE["✅ write concept
(compass / wiki)"] D -- "no, attempts left" --> REVISE["spawn revise task
or client.revise()"] REVISE --> CRITIC D -- "no, max attempts" --> DROP["❌ drop — no file written"]
Two paths to synthesis (sync loop vs async queue), one deterministic critic gate.

The critic loop (sync variant)

sequenceDiagram participant G as generator participant C as critic_concept participant DB as .kg participant B as OKF bundle loop up to MAX_REVISE_CYCLES+1 G->>G: client.synthesize or client.revise G->>C: critic_concept(draft) C->>DB: verify file refs and symbol refs DB-->>C: exists per ref C-->>G: passed / errors / quality_score G->>G: break if no errors end G->>B: write_concept only if accepted
The critic runs after every synthesize/revise; the loop stops on zero errors. Same gate in the async queue path.

7. Memory lifecycle

Memory is a four-tier system with promotion, decay, and live verification against the graph.

flowchart LR CAP["capture_memory
agent records learning"] CAP --> SCORE["score_memory
6 weighted signals"] SCORE --> TIER{"score?"} TIER -- "< 0.3" --> RAW["raw/
ephemeral"] TIER -- "< 0.5" --> DRAFT["drafts/
awaiting critic"] TIER -- ">= 0.5" --> TRIBAL["tribal/
durable — read these"] RAW -. "decay >7d" .-> ARCH["archived/"] TRIBAL -. "stale >90d" .-> ARCH DRAFT -. "batch_critic
promote" .-> TRIBAL TRIBAL -. "force promote" .-> CANON["canonical
compass / wiki"] RECALL["recall_memory / digest"] TRIBAL --> RECALL RECALL -. "live refs-verified
fraction vs graph" .-> VERIFY["L1 graph check"]
Memory tiers: raw → drafts → tribal → (promoted to canonical), with archived as the decay sink.

6 scoring signals: 0.25·graph_verification + 0.20·cross_session_refs + 0.15·agent_confidence + 0.20·critic_score + 0.10·freshness + 0.10·authority. The standout feature: recall_memory recomputes the refs-verified fraction live — a memory citing renamed code self-invalidates.

8. Storage layout

Two stores side by side, both local, both readable.

SQLite (.kg)

├── memory/

Every concept is a markdown file with YAML frontmatter (OKF v0.2). memory_signals caches the score; memory_tier tracks the lifecycle stage; generated.by records the last producer.
